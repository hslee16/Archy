## Belongs in this change

**1. Children inherit relative `PATH` entries.** I reproduced this with `PATH=".:&lt;abs&gt;:/usr/bin:/bin"` and the project as the working directory:
- **Real `uvx`:** the project's `./python3` ran during uv's interpreter discovery. I ran it offline with an empty managed-Python directory. A machine with a uv-managed Python may not search `PATH` at all.
- **Wrapper with `#!/usr/bin/env bash`** (the shape pyenv and asdf shims take, using a stand-in `archy`): the project's `./bash` ran.
- **Python child calling `git` by name** (stand-in script): the project's `./git` ran. archy does this itself in `gitlog.py`, `coupling.py`, `hotspots.py` and `history.py`.

The fix is to sanitise the `PATH` passed on to children, for example near the top of the launcher:
```js
process.env.PATH = (process.env.PATH || "").split(delimiter).filter(isAbsolute).join(delimiter);
```
In a temp copy, this turned the real-`uvx` case from "project python ran" to clean. The `bash` and `git` cases use the same inherited `PATH`, but I did not re-run them with the patch. It needs a test where an absolute fake tool calls a bare command and the project plants that command.

**2. The `cmd.exe` test is too weak.** I mutated only a temp copy:

| Mutation | New tests |
|---|---|
| `.filter(Boolean)` (protection removed) | 6 fail (good) |
| Block only `.` | 3 fail (good) |
| Block only named relative directories | 3 fail (good) |
| `command: "cmd"` | 1 fails (good) |
| `command: 'cmd'` | **all pass** |
| `command: "cmd.exe"` | **all pass** |
| `CMD_EXE = process.env.ComSpec \|\| "cmd"` | **all pass** |

The `PATH` tests are sound. The `cmd` test only matches source strings. Either assert the exact `CMD_EXE` definition and `command: CMD_EXE`, or run `spawnArgs` with a stubbed platform.

## Separate ticket

- **Windows batch wrappers (reasoned, not run):** inside a `.cmd` or `.bat` file, `cmd.exe` searches the working directory for bare commands whatever `PATH` says. So a shim that calls `python` or `node` by name could run the project's copy. Setting `NoDefaultCurrentDirectoryInExePath=1` in the child environment should close this. It is a one-liner, so it could also go in this change if you can check it on Windows.

## Legitimate setups

- **Relative `PATH` entries** such as `.venv/bin` or `node_modules/.bin`: an `archy`, `uvx` or `python` found only that way is no longer used. This is intended, but the error then says "found no `archy` or `uvx` on PATH", which could confuse. It is worth a line in the plugin README.
- **Child tools under the suggested fix:** tools reachable only through a relative entry would also disappear for child processes.
- **Quoted, `~` or unexpanded `%VAR%` entries:** I see no regression, since the old lookup did not expand them either.
- **Absolute entries inside the project** (an activated venv, direnv's `PATH_add`): these still run. That is the user's own configuration.
