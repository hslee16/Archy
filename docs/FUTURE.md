# Future Features

Concrete things to build next, with rough order. Items in brackets cite where the idea came from. Items annotated `[RESEARCH_METRICS.md §N]` are validated against the survey in [`RESEARCH_METRICS.md`](RESEARCH_METRICS.md).

## Pre-call-graph wins (validated, low cost)

These are essentially free - no new edge type, no AST work, no git mining - and would substantially widen archy's signal surface before the call-graph PR lands.

- ~~**Tangle ratio**~~ shipped in v0.7.x as `acyclicity = 1 - tangle_ratio` (fraction of nodes inside SCCs of size ≥ 2). Replaced the old `1/(1+cycle_count)` form. See `docs/SCORING.md` §Acyclicity. [RESEARCH_METRICS.md §6]
- ~~**`archy.yaml` Forbidden + Independence contracts**~~ shipped in v0.8.x as `archy contracts` / `archy_contracts` MCP tool. Wraps import-linter rather than reimplementing natively (~1/3 the LOC, gets all five contract types: Layers, Forbidden, Independence, Protected, AcyclicSiblings). Reads `.importlinter`. Optional dep behind `archy[contracts]`. [RESEARCH_METRICS.md §10; docs/AGENT_LOOP_CONTRACTS_TEST.md]
- ~~**NCCD / MacCormack propagation cost diagnostic**~~ shipped in v0.13.3 as a per-project field on `archy score`'s `inputs.propagation_cost`, a per-target field on `archy_impact`'s response (`|changed ∪ impacted| / N_internal`), and a per-node field on `archy graph --format json` / `archy_graph` / `archy_graph_focus` / `archy_graph_summary`. The 27-project bench-sweep distribution looks sensible: wide-and-shallow plugin architectures bottom out below 0.05 (pygments 0.023, setuptools 0.05), tightly-coupled small projects top out near 1.0 (msgspec 0.91, aiohttp 0.83, flask 0.81), well-modularized large projects sit at 0.15-0.30 (django, numpy, ansible). Diagnostic only; not yet a score axis. **Open follow-up**: promote to fifth score axis at a deliberate version boundary (v0.15+, after call graph) with the OECD comparability-over-time guidance flagged in `SCORING.md`. [RESEARCH_METRICS.md §3; MacCormack et al. 2006, "Exploring the Structure of Complex Software Designs"]
- ~~**Martin's `I` per module + SDP-violation check rule**~~ shipped. `compute_instability` exposes per-module `I = Ce/(Ce+Ca)` in `archy graph --format json`; opt-in `sdp:` block in `archy.yaml` makes `archy check` flag any internal edge whose target is strictly less stable than the source. [RESEARCH_METRICS.md §2]
- **PageRank + core size as diagnostics** - per-module PageRank weights "importance by importance of dependents." Core size = largest SCC fraction. Both are NetworkX one-liners. Surface in `archy graph --format json` and `archy_impact` output; not score axes. [RESEARCH_METRICS.md §3, §5] (PageRank also lands in the `archy_graph_summary` MCP tool per [`SPEC_GRAPH_MCP.md`](SPEC_GRAPH_MCP.md).)
- ~~**`archy_graph` MCP tool**~~ shipped. Three lenses (`archy_graph_focus`, `archy_graph_summary`, `archy_graph`) so an agent can navigate the dep graph without dumping it whole. Full design in [`SPEC_GRAPH_MCP.md`](SPEC_GRAPH_MCP.md). PageRank is hand-rolled (NetworkX 3.x's pagerank now requires numpy/scipy, which archy avoids).
- ~~**`.importlinter` as canonical contracts config**~~ shipped in v0.15.0. The archy.yaml→Forbidden translation path is demoted to a best-effort zero-config onramp and now emits a `UserWarning` when it fires, because it cannot express `ignore_imports` (legitimate transitive edges have no way to be whitelisted, so projects with a sanctioned cross-layer access pattern get permanent false-positives (the psycopg-through-db-engine case from the 2026-05 agent loop)). README, docstrings, and the missing-config error all point at `.importlinter` first; archy.yaml stays focused on layers + direct-edge gating + the metrics import-linter doesn't do (`sdp:`, `exclude:`, `roots:`). The two-config split is deliberate: each file does one thing.
- ~~**Per-module edit-risk composite for agents**~~ shipped in v0.14.0 as `edit_risk` on internal nodes in `archy graph --format json` / `archy_graph` / `archy_graph_focus`, a `top_edit_risk` block in `archy_graph_summary`, and a new `archy_high_risk_modules` MCP tool. Composite is the geometric mean of MacCormack propagation cost, normalized fan-in, and Martin's instability - all three terms have to be non-trivially high for the score to be high, biasing the signal toward *central and fragile* modules. The 27-project bench sweep is intuitive: load-bearing semantic centers dominate (msgspec.msgspec 0.72, click.core 0.60, httpx._models 0.59, flask.app 0.55, requests.models 0.55, rich.console 0.51, pytest.config 0.48, mypy.nodes 0.31, django.models 0.23). Small tightly-coupled projects peak high; wide plugin architectures (pygments 0.22, setuptools 0.19) stay flat. Diagnostic only - not folded into `archy score`'s overall number. [Navigation Paradox 2026; Columbia DAPLab "9 Critical Failure Patterns"; RESEARCH_METRICS.md §14]
- **Static fragility proxy as a pre-CC hotspot stand-in** - high-instability × high-fan-in modules. Captures "central and volatile" without the git-history overhead of the full hotspots feature below. Won't match CodeScene's churn-weighted hotspot precision but ships today and gives agents a first-cut "be careful here" signal. Surface as a new MCP tool or as part of `archy_graph_summary`. Mark explicitly as a proxy; the git-history version remains the higher-quality target. [CodeScene "Code Health" Code Red paper for the gold-standard formulation]
- **Docs: cite the Navigation Paradox / LocAgent empirical validation in `LEARNINGS.md`** - the Feb-2026 "Navigation Paradox in Large-Context Agentic Coding" paper and LocAgent (ACL 2025) are direct empirical evidence that AI coding agents need structural graph navigation and that invoke/import edges materially improve code-localization accuracy. Adding a short references section in `LEARNINGS.md` (or a new `WHY_AGENTS_NEED_THIS.md`) hardens archy against the "where's the proof?" critique and gives users a citable rationale for adopting the MCP loop. Pure docs task; ~30 minutes. [`arxiv:2602.20048`, `aclanthology:2025.acl-long.426`]

## Near-term (next 2–3 PRs)

- ~~**Call graph**~~ shipped in v0.16.0 as a *diagnostic*: tree-sitter `(call) @call` extraction, import-alias resolution of the leftmost identifier, per-edge `kinds: tuple[str,...]`, `call_lines`, `call_count` attributes exposed in `archy graph --format json` and across the MCP graph tools. Per-graph aggregates `total_calls`, `call_edge_count`, `calls_per_edge` surfaced on `archy score`'s `inputs`. Empirical orthogonality on the 27-project bench is strong (`|r| ≤ 0.23` against all four existing axes plus propagation cost - by far the most orthogonal signal archy has added since v0.2; see [`RESEARCH_METRICS.md` §16](RESEARCH_METRICS.md)). Score-axis promotion (weighted modularity vs new fifth axis) is deferred to a deliberate version boundary so OECD comparability-over-time guidance is respected - same precedent v0.13.3 set with MacCormack propagation cost.  **Open follow-up**: call-weighted Newman Q as a refinement of the modularity axis. The "new coupling axis" alternative was reviewed in v0.20 and rejected; see [`docs/AXIS_REVIEW.md`](AXIS_REVIEW.md) for the directionality / actionability / discriminant-validity argument. [LocAgent §ablation; sentrux: uses both import and call edges in Q]
- ~~**Cyclomatic complexity per function**~~ shipped in v0.17.0 as a *diagnostic*: tree-sitter walker in `src/archy/complexity.py` extracts per-function McCabe CC over the existing AST (branch nodes: if/elif/for/while/except/case/conditional_expression/boolean_operator/comprehension-clauses). Per-module aggregates (`function_count`, `cc_sum`, `cc_max`, `cc_mean`) attach to every internal node in `archy graph --format json`; project-wide aggregates surface on `archy score`'s `inputs` (`function_count`, `cc_total`, `cc_max`, `cc_mean`). The 27-project bench shows `cc_mean` is even more orthogonal than v0.16's call density: max `|r| = 0.197` against the four score axes plus propagation cost plus calls-per-edge (see [`RESEARCH_METRICS.md` §17](RESEARCH_METRICS.md)). Cognitive complexity is **not** included in this PR despite the original "rides along free" claim - the Sonar definition needs nesting-depth bookkeeping that doesn't share the same single-pass walker. Type-hint coverage same status. Both are open follow-ups using the same `function_definition` AST surface. **Open follow-ups**: (1) ~~promote `cc_mean` to a score axis~~ done in v0.20.0 as `complexity = 1 - clamp((cc_mean - 1) / 5, 0, 1)`; call-density follow-on still open; (2) ~~ship `archy hotspots = CC x per-file churn`~~ done in v0.18.0.
- **Design Structure Matrix (`archy dsm`)** - render the internal dependency graph as a square module x module 0/1 matrix with rows/columns ordered to push edges below the diagonal (topological where possible, blocked by SCC for cyclic regions). The DSM is the canonical industrial visualization of architectural coupling (Steward 1981, Eppinger & Browning); it's complementary to the import-graph dump because it makes block structure, cycles, and layer leakage visible at a glance. Surface as a new CLI command (`archy dsm PATH --format text|json|html`) and an MCP tool; ASCII output for terminal sessions, JSON for downstream tooling, optional self-contained HTML for CI artifacts. Diagnostic only - not a score axis. Pairs naturally with the contracts work because the matrix immediately shows which contracts are load-bearing. [MacCormack et al. 2006 use DSM as the substrate for propagation cost; Steward 1981; Eppinger & Browning, *Design Structure Matrix Methods and Applications*]

## Scoring (the headline feature)

- ~~**Single quality score**~~ shipped in v0.2.0 as `archy score`. Four sub-metrics (modularity, acyclicity, depth, equality), geometric mean. Side-by-side comparison with sentrux's design in `docs/LEARNINGS.md`.
- ~~**Per-commit JSONL history** in `.archy/history.jsonl`~~ shipped in v0.3.0 (`archy score --record`).
- ~~**`archy trend`**~~ shipped in v0.3.0 - ASCII sparkline + last-N table.
- **Static HTML trend report** - the original stretch goal. Render `.archy/history.jsonl` as a self-contained HTML page with Chart.js so trend can be linked from a CI artifact or dashboard.
- **Equality based on per-function CC** - we currently compute Gini over module out-degrees as a proxy. The eventual signal is `gini(per_function_cyclomatic_complexity)`, which requires the cyclomatic-complexity metric above.
- **Type-hint coverage as sub-stat or sixth axis** - percentage of public functions with full parameter and return annotations. Differentiated Python signal that no graph-level metric captures. Tree-sitter pass over `FunctionDef` nodes; rides on the same AST scope as cyclomatic complexity. Could ship first as a sub-stat and promote to a score axis if the signal proves load-bearing. [RESEARCH_METRICS.md §13]
- ~~**Hotspots = CC × per-file churn**~~ shipped in v0.18.0 as `archy hotspots` (CLI; module in `src/archy/hotspots.py`). Single `git log --name-only --format=` pass yields per-`.py`-file commit counts; the rank is `cc_sum * churn` per internal module, with zero-CC and zero-churn rows filtered out so the list flags only files that score on both axes. Produces a prioritized "refactor these first" list rather than a single number; diagnostic only, not folded into `archy score`. The 27-project `--since` window sweep (`bench/hotspots_sweep.py`, results in `bench/hotspots_results.md`) settled the default empirically: full history wins because it produces a stable top-K on every project (12-month windows collapse to <20 items on low-activity codebases like mkdocs and httpx), with ~25% median recency contamination as the tradeoff; the `--since` flag is documented as the "what should I refactor right now" lens. Median Jaccard(full, 12mo) = 0.60 across the bench; J(12mo, 6mo) = 0.74, so the meaningful window boundary is "full vs ≤12 months", not "12 vs 6". The MCP-tool surface (`archy_hotspots`) followed in v0.19.0; when the project isn't under git, the tool returns an empty list plus a `note` pointing at `archy_high_risk_modules` as the structural fallback rather than raising or faking churn=1. [RESEARCH_METRICS.md §8; Tornhill, *Your Code as a Crime Scene*]

## Deferred - needs more thought

- **Duplicate-function detection** - AST-shape hashing (normalize identifiers, hash structure, cluster) over a length threshold. Lower empirical FP rate than dead-function detection. Ship as an advisory list, not a score axis. [sentrux: `redundancy_ratio`; RESEARCH_METRICS.md §12]
- ~~**Dead-function detection**~~ - **deferred indefinitely.** Empirical 23-project vulture run in 2026-05 confirmed default-confidence FP rates from 10 (msgspec) to 2,017 (django); 15-finding spot-checks on FastAPI / pytest / Django were 15/15 false positives, dominated by Pydantic validators, pytest fixtures, decorator-registered route handlers, and Django's `global_settings.py` string-lookup pattern. Static dead-code detection on real Python is too noisy to fold into a quality signal. Revisit only if archy can ingest a runtime-coverage source. [RESEARCH_METRICS.md §12]
- **Score-shape redesign for axis independence.** The 23-project benchmark shows 4 of 6 axis pairs at moderate Pearson correlation (`|r|` 0.5-0.7), all below the OECD redundancy threshold but enough to qualify the geometric-mean independence argument. Two candidate redesigns: (a) replace acyclicity's tangle-ratio normalization with a graph-size-invariant alternative to break its coupling with depth and equality; (b) accept the coupling and replace geometric mean with a non-compensatory aggregator that handles correlated indicators explicitly (e.g., Mazziotta-Pareto Index). Both are research projects, not roadmap items today. [SCORING.md §Empirical axis independence]
- **Type reference edges** - function parameter and return annotations as a third edge type. Useful for catching layer violations that hide behind `if TYPE_CHECKING:` imports. [sentrux: `tags.scm` type-reference query]
- **Treemap visualization** - D3 or Observable Plot, wrapped in a static HTML report. Sentrux's signature feature; valuable but not load-bearing for governance use.
- **Deterministic contract-check hook for AI sessions.** Empirical finding from the agent-loop test in `governingdocs/backend` (2026-05): a fresh agent caught a forbidden cross-layer import before implementing it, but did so by reading `archy.yaml` + `CLAUDE.md` directly rather than calling `archy_check` / `archy_contracts`. The MCP-tool angle's marginal value over "agent reads docs" is narrower than the hypothesis assumed - it shows up mainly when rules live only in `.importlinter` (no archy.yaml) or when violations are transitive multi-hop. To make contract-check feedback deterministic regardless of agent disposition, ship a Claude Code Stop hook that runs `archy contracts` once per task and surfaces violations into the agent's context. Per-task cost: ~3-5s wall, ~150-600 tokens. PostToolUse-on-Edit fires too often (5-15x per task, edit-thrashing noise). Project-side configuration only; archy doesn't need new code. Worth shipping as a documented snippet in `docs/AGENT_LOOP.md`, not a feature.
- ~~**Pre-commit hook + GitHub Action**~~ shipped in v0.4.1/v0.4.2 - see `README.md` for usage.

## Hard problems that probably won't ship

- **Dynamic imports** - `importlib.import_module(name)` where `name` is a runtime string. Static analysis can flag these as opaque but can't resolve them. Acceptable.
- **Conditional imports under `sys.platform` / `TYPE_CHECKING`** - currently treated as unconditional. We could tag edges with their guarding condition for richer rules ("CI must not depend on Windows-only modules") but the YAML schema for that is non-trivial.

## Anti-goals (stay disciplined)

- **Python only - settled, not up for revisit.** The multi-language story belongs to sentrux. The division is final; this is not a tradeoff to reopen or iterate on, and the roadmap should never spend effort defending it. See `LEARNINGS.md` §"Competitive landscape" for the broader bucket map and why depth-on-Python is archy's defensible wedge.
- No runtime instrumentation (only static analysis). The whole pitch is "doesn't need to run your code."
- No replacement of linters or type checkers. We're orthogonal to ruff and mypy, not a competitor.
