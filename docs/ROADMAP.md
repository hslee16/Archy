# Roadmap

Short, opinionated summary of where archy is going. The detailed item-by-item list (with shipped, in-flight, deferred, and rejected items, plus citations to the literature each idea came from) lives in [`FUTURE.md`](FUTURE.md). This page is the executive summary.

## Audience principle (load-bearing)

archy's outputs are consumed by **LLM coding agents**, not by humans browsing dashboards. This frames every decision below:

- Useful output shapes: structured JSON (MCP tools, `--format json`), terminal ASCII (for agent "show your work" context), and the snapshot/diff loop.
- Not useful output shapes: rendered HTML dashboards, interactive web visualizations, anything that requires a browser to consume.

When deciding whether to ship a feature, the load-bearing question is "what does this give an agent that it doesn't have today?", not "would this look nice as a chart?".

## Now

Things actively in flight or planned for the next 2-3 releases. Items previously in this section shipped in v0.21.0 / v0.22.0 / v0.24.0 / v0.25.0; the queue below promotes from "Next" as work picks up.

Both phases of [`SPEC_INDEX_AND_INSTALL.md`](SPEC_INDEX_AND_INSTALL.md) have shipped (Phase 1 install-DX in v0.25.0/v0.26.0, Phase 2 persistent index + watcher in v0.27.0); see "Shipped from this section" below. The remaining queued items are in "Next".

### Shipped from this section

- ~~Phase 2: persistent index + file watcher~~ shipped in v0.27.0 ([#116](https://github.com/hslee16/archy/pull/116) cache, [#118](https://github.com/hslee16/archy/pull/118) watcher + `archy_status`). Part 1: `src/archy/index.py` caches each file's `ParseResult` in `.archy/index.db` keyed by content hash and re-parses only what changed, then re-runs the existing global resolution, so a cache-backed build is byte-identical to a cold one (the property the test suite asserts). Benchmarked 7-9x warm-path speedups on Django (2.9k modules), pytorch (4.5k), and Home Assistant (17.3k); parsing is ~85% of cold build cost and resolution stays ~3%, which is why the cache boundary is the parse, not the resolved graph, and why incremental resolution was rejected. Part 2: `src/archy/watcher.py`'s `IndexManager` holds one persistent cache connection per project root and a `watchdog` observer that runs the sync in the background on a 2-second debounce (`threading.Timer` reset per Python-file event), all serialized by one lock; the `archy mcp` server keeps a per-root manager registry so repeated tool calls reuse a warm, background-synced index. A new `archy_status` MCP tool (the 17th) reports `last_synced_at`, `cached_files`, and whether the watcher is running. The watcher is a latency optimization, never a correctness mechanism: every tool still syncs on demand, so a result is never stale even if an event was missed or the watcher could not start. Remaining optional follow-up: the churn column (git-log-populated, surfaced in `archy_hotspots`).

- ~~Agent-detecting installer registry (`archy install` / `archy uninstall`)~~ shipped in v0.26.0 ([#112](https://github.com/hslee16/archy/pull/112) install, [#113](https://github.com/hslee16/archy/pull/113) uninstall + docs). Phase 1 (third leg) of [`SPEC_INDEX_AND_INSTALL.md`](SPEC_INDEX_AND_INSTALL.md), closing the install-DX leg. `archy install` auto-detects which agent clients (Claude Code, Cursor, Codex CLI, opencode, Continue) are present, writes each one's MCP server stanza, drops the rules file each expects (`.cursor/rules/archy.mdc`, `~/.codex/AGENTS.md`, ...), and for Claude Code seeds the `permissions.allow` allowlist the plugin manifest cannot write (closing the #104 gap). Architecturally an "adapter registry": one small adapter per client in `src/archy/install/adapters/`, cross-platform from day one (detection layers `shutil.which` over per-OS config-path probes with macOS-app-bundle / Windows-install-dir fallbacks). `archy uninstall` is the symmetric inverse: each adapter declares paired `render`/`unrender` per file, so uninstall strips archy from shared configs (leaving the rest byte-for-byte) and deletes archy-owned files; idempotent. Non-interactive flags (`--yes`, `--target`, `--print-config`, `--dry-run`) for CI / scripting. Five-layer test strategy (unit, snapshot, filesystem integration, contract, gated E2E) per [`SPEC_INSTALL_TESTING.md`](SPEC_INSTALL_TESTING.md), running on the ubuntu/macos/windows matrix. User-facing docs: [`INSTALL.md`](INSTALL.md).
- ~~`archy affected` CLI + `archy_affected` MCP tool~~ shipped in v0.25.0 ([#103](https://github.com/hslee16/archy/pull/103)). Phase 1 (first leg) of [`SPEC_INDEX_AND_INSTALL.md`](SPEC_INDEX_AND_INSTALL.md). Maps changed files to impacted modules and test files via a depth-capped reverse-impact walk (default 5 hops) so monorepo edits stay tractable, with the impacted set pre-classified into `impacted_tests` (pytest convention by default, recursive-glob override via `--filter`) and `impacted_modules`. CLI shape is `git diff --name-only HEAD | archy affected . --stdin -q | xargs pytest`; MCP shape mirrors the same payload. Internal modules only at launch; `--include-external` follow-up captured in [`FUTURE.md`](FUTURE.md). Inspired by [colbymchenry/codegraph](https://github.com/colbymchenry/codegraph)'s `affected` command, scoped to archy's judge-not-librarian role (see [`LEARNINGS.md`](LEARNINGS.md) bucket 6).
- ~~Claude Code plugin~~ shipped in v0.25.0 ([#104](https://github.com/hslee16/archy/pull/104)). Phase 1 (second leg) of the install-DX work. Bundles the MCP server registration (`uvx archy>=0.25 mcp`) and the canonical `archy` skill into an installable unit at `plugins/claude/`; users run `claude --plugin-dir /path/to/archy/plugins/claude` to install. Two limitations of the current Claude Code plugin loader documented inline: plugin manifests cannot seed `permissions.allow` (paste-into-`settings.json` snippet shipped in the README instead) and cannot bundle a project-level `CLAUDE.md` (instruction context flows through the bundled skill). Drift between the canonical `skills/archy/SKILL.md` and the plugin's mirror is pinned by `tests/test_plugin.py`.
- ~~Smarter `archy_diff` summary~~ shipped in v0.24.0. `archy diff` / `archy_diff` returns an additive `DiffSummary` block (`headline`, `top_regressions`, `top_improvements`) ranked by `compute_edit_risk` so the loop-closer step doesn't have to scan and re-rank raw deltas. Detail lists stay; ranking is additive so existing consumers don't break. Cycle descriptions truncate to 5 members + `(+N more)` to keep dagster-sized SCCs readable. Empirical perf on the 28-repo dogfood: `summarize_diff` is 0.1-0.5% of total `archy diff` runtime even on the largest real repos, so shipped additive with no opt-out. MCP `loop` prompt and `AGENT_LOOP.md` updated to direct agents to read `summary.headline` first.
- ~~`archy dsm` (Design Structure Matrix)~~ shipped in v0.22.0 as a visualization-only output. CLI `archy dsm PATH` + MCP tool `archy_dsm`, with `--group=community|layer|topological`, `--weight=imports|calls`, `--focus`/`--package` filters, and `--diff` returning a `DSMDiff` whose `new_back_edges` field flags cycles an edit just introduced. ASCII for terminal context, JSON for tool consumption; HTML output dropped per the audience principle. Empirical study against the 27-project bench ruled out promoting any DSM-derived scalar to a score axis or diagnostic ([`DSM_EMPIRICS.md`](research/DSM_EMPIRICS.md)).
- ~~Call-weighted Newman Q as a refinement of the modularity axis~~ shipped in v0.21.0 as a parallel diagnostic on `archy score` rather than an axis replacement. The gap between unweighted and weighted Q is the load-bearing signal (it detects mismatch between import-graph and call-graph community structure). Replacement was rejected because directionality is contested for intentional small-core / broad-call shapes ([`CALL_WEIGHTED_Q_EMPIRICS.md`](research/CALL_WEIGHTED_Q_EMPIRICS.md)).
- ~~`archy_what_to_refactor_next` MCP tool~~ shipped in v0.30.0 ([#130](https://github.com/hslee16/archy/issues/130)). One ranked refactor-priority list (CLI `archy what-to-refactor-next` + MCP `archy_what_to_refactor_next`, the 19th tool) fusing the behavioral lens (`archy_hotspots`, CC x churn) and the structural lens (`archy_high_risk_modules`, edit-risk): candidates come from both, and the fused `priority` (each lens normalized to its project max, then summed) ranks a module flagged by *both* lenses above a comparable single-lens one, while still letting a dominant single-lens signal (a giant hotspot at the import-graph leaves) top the list. Each entry names which lenses fired plus a one-line `rationale`. Pure aggregation over the two existing primitives in `src/archy/refactor.py`; no new analysis. Honest null is load-bearing: the candidate set is empty (and the tool returns a `note`, not a phantom #1) when nothing is both complex and churned and nothing clears the `min_risk` structural floor (default 0.15) - a real "nothing to prioritize" answer for small, young, or clean projects. Git-absent degrades to the structural lens alone, mirroring `archy_hotspots`.

## Next

Things validated and queued but not yet started.

- **Per-module score breakdown** ([#129](https://github.com/hslee16/archy/issues/129)). Today `archy score` is project-wide. A per-module breakdown lets an agent ask "did my edit make *this module* worse?" rather than "did the project overall regress?". Pairs with `archy_diff`.
- **Change coupling (temporal coupling)** ([#131](https://github.com/hslee16/archy/issues/131)). Rank module *pairs* that frequently change together in git history but have no import or call edge between them: a hidden dependency or a missing abstraction the structural graph can't see. The behavioral complement to the import graph, from the same Tornhill / CodeScene behavioral-code-analysis lineage `archy_hotspots` already draws from; reuses the existing git-churn machinery. Agent-actionable ("you're editing X; historically Y changes with it, check Y") and a judge-role verdict, not a code dump. Needs an empirical-validation pass first (co-change is noisy: commit-size normalization plus a coupling-strength threshold, à la the dead-code FP study) before it ships, and a decision on advisory-diagnostic vs anything score-bearing. Surfaced by the 2026-05 competitive scan as the one feature gap that fits archy's niche.
- **Duplicate-function detection** ([#133](https://github.com/hslee16/archy/issues/133)) via AST-shape hashing. Advisory list, not a score axis.
- **Static fragility proxy** ([#134](https://github.com/hslee16/archy/issues/134), `good first issue`) as a pre-CC hotspot stand-in (high-instability x high-fan-in modules). Ships today without git-history overhead; the full hotspots feature (already in v0.18) remains the higher-quality target.
- **Opt-in agent hooks (`archy install --hooks`)** ([#132](https://github.com/hslee16/archy/issues/132)). Register a lifecycle hook in the agent client (Claude `Stop`, Cursor `afterFileEdit`, Codex `post-edit`/`notify`, opencode plugin; Continue has no hooks) that runs the archy gate (`archy score --strict` / `archy diff`) automatically after edits, so the feedback loop fires whether or not the agent remembers to call the tools. Opt-in and advisory by default; reuses the install adapter registry's render/unrender pattern so `archy uninstall --hooks` is the exact inverse. Made affordable by the persistent parse cache. Spec: [`SPEC_INSTALL_HOOKS.md`](SPEC_INSTALL_HOOKS.md).

## Deferred (needs more thought)

- ~~**Score-shape redesign for axis independence.**~~ Studied in 2026-05 ([`SCORE_SHAPE_REDESIGN_EMPIRICS.md`](research/SCORE_SHAPE_REDESIGN_EMPIRICS.md)) and concluded against any axis change. Seven acyclicity variants and three depth variants were evaluated against the 28-project bench; the only combinations that reach `0/10` moderate pairs require a depth-axis redesign (`depth_with_scc_penalty`) that fails the OECD actionability gate (conflates "new long chain" with "new SCC" into one number), and every such combination shakes the project leaderboard substantially (Spearman ρ vs v0.23 in `[0.53, 0.64]`). A separately tractable aggregator change (Mariani-Ciommi penalized geometric mean) remains open as a soft recommendation but is not blocking; the moderate pairs all involve `depth`, which under every tested aggregator correlates only weakly with `overall` (`|r| ≤ 0.187`), making the OECD breach operationally cosmetic.
- **Equality based on per-function CC.** Currently a proxy via Gini over module out-degrees. The eventual signal is `gini(per_function_cyclomatic_complexity)`; requires the cyclomatic-complexity metric (shipped in v0.17, promoted to a score axis as `complexity` in v0.20), but the substitution itself has not been validated yet.
- **Positive exemplar surfacing (`archy_exemplars`)** ([#138](https://github.com/hslee16/archy/issues/138)). The inverse of `archy_high_risk_modules`: rank the *cleanest* peer module as a copy-me template, because the Constraint Decay HN thread's most-repeated practical finding is that showing an agent a good example beats describing the rule in prose. Design resolved corpus-free and project-relative ([`RESEARCH_METRICS.md` §14c.5](research/RESEARCH_METRICS.md)): archy is the **structural-quality ranker, not the retriever** (similar-code retrieval is the IDE/RAG layer's job and is net-negative when quality is uncontrolled; example *quality* is what dominates ICL outcomes), and "pattern" means a peer group that already exists in the repo, scored by within-group structural health, so it never goes stale. Scoped as an **epic, not a Next item**: gated on the per-module score breakdown (#129), still needs a clean-but-trivial guard and a bench validation that "structurally cleanest peer" tracks "useful exemplar." [Constraint Decay HN; [`FUTURE.md`](FUTURE.md); RESEARCH_METRICS.md §14c.4-5]
- **Rule-rot / constraint-staleness detection** ([#139](https://github.com/hslee16/archy/issues/139)). The mirror image of constraint decay: agents obey constraints but cannot tell when a constraint itself is stale, so they satisfy it with inelegant indirection rather than revising it. archy can see the symptom (a `forbid` rule with many `ignore_imports` exceptions; indirection edges that exist only to route around a layer boundary). Scoped as an **epic, not a Next item**: separating "the rule is stale" from "the code is wrong" needs a dead-code-style FP study (the v0.15.0 false-positive lesson is the cautionary precedent) before anything ships. Advisory only if it ever ships. [Constraint Decay HN; [`FUTURE.md`](FUTURE.md); RESEARCH_METRICS.md §14c.4]

## Rejected (explicitly will not ship)

- **Type-hint coverage in any form (axis or diagnostic).** Empirical study in 2026-05 ([`TYPE_HINT_COVERAGE_EMPIRICS.md`](research/TYPE_HINT_COVERAGE_EMPIRICS.md)) concluded against both axis promotion (independence is the weakest archy has measured, max `|r| = 0.551`; discriminant validity is contested) and diagnostic shipment (mypy / pyright own the typing niche, the signal is not structural, and the "single sensor for everything" framing would dilute archy's graph-shape focus). The bench script and raw numbers stay in `bench/` for future reconsiderations.
- **`calls_per_edge` as a 6th score axis.** Empirical study in 2026-05 ([`AXIS_REVIEW.md`](research/AXIS_REVIEW.md)) concluded against axis promotion on directionality / actionability / discriminant-validity grounds even though independence passes. The call data is genuinely useful and shipped as: a diagnostic on `archy score`, the v0.21 call-weighted Newman Q parallel diagnostic, and the LocAgent-style `archy_graph_*` MCP navigation tools.
- **HTML output formats for archy commands.** Per the audience principle: agents consume structured JSON and terminal ASCII, not browser-rendered HTML. The original "static HTML trend report" v0.3 stretch goal and the "self-contained HTML for CI artifacts" framing of `archy dsm` are both retired. If a human dashboard is ever needed, third-party tools can consume archy's JSON output.
- **Dead-function detection.** Empirical 23-project vulture run in 2026-05 confirmed default-confidence false-positive rates from 10 (msgspec) to 2,017 (django); 15-finding spot-checks on FastAPI / pytest / Django were 15/15 false positives, dominated by Pydantic validators, pytest fixtures, decorator-registered route handlers, and Django's `global_settings.py` string-lookup pattern. Static dead-code detection on real Python is too noisy to fold into a quality signal. Revisit only if archy can ingest a runtime-coverage source.
- **Multi-language analysis.** Out of scope; that division of labor with [sentrux](https://github.com/sentrux/sentrux) is settled. archy goes deep on Python instead of broad across languages.
- **Code generation or auto-fix.** archy is a sensor, not a fixer. Surfacing the problem is the value.
- **DSL or plugin system for layer rules.** YAML stays YAML. If you need more expressive contracts, use `archy contracts` (which wraps import-linter) instead.
- **Docstring coverage, test coverage, license scanning, `__all__` consistency, public-API churn, or similar "complete-codebase-health" diagnostics.** Same argument that killed type-hint coverage: better tools own these niches and adding them would dilute archy's graph-shape focus. archy is a graph-shape sensor; it is not the single source of truth for "is this codebase healthy."

## How this list changes

When a "Now" item ships, it moves to a bullet in the README's "Shipped" section and gets a citation in [`FUTURE.md`](FUTURE.md) with the validation evidence. When a "Next" item gets prioritized, it moves to "Now." Items move into "Deferred" or "Rejected" only when there is empirical evidence (a benchmark sweep, an FP-rate study, a concrete user pain point) or an explicit value-prop argument (the audience principle, the structural-niche focus), not on speculation. Every shape change to this list lands as a PR so the history is in git.

See [`FUTURE.md`](FUTURE.md) for the long-form list with citations, [`docs/research/RESEARCH_METRICS.md`](research/RESEARCH_METRICS.md) for the literature survey that informs prioritization, [`docs/research/AXIS_REVIEW.md`](research/AXIS_REVIEW.md) for the OECD framework used on every axis-promotion decision, and [`docs/LEARNINGS.md`](LEARNINGS.md) for design rationale on shipped decisions.
