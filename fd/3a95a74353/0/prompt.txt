## SEVERITY 4 — The run-order confound is real and measurable, and is not the admitted breadth confound

`run_pair` (`agent_footprint.py:436-437`) always iterates `("A", …), ("B", …)` — A is never second. The writeup calls this "interleaved" (`:134`), which covers *between*-pair drift but not *within*-pair order.

The data shows a one-sided drift. Spearman vs `run_index`:

| series | rho |
|---|---|
| A `pre_edit_reads` | **+0.782** (past the n=10 0.05 critical value of ~0.648) |
| B `pre_edit_reads` | +0.248 |
| A `num_turns` | +0.491 |
| B `num_turns` | −0.055 |

A's reads climb 7 → 13 across the run; B's are flat. Since A always ran first, variant and within-pair position are perfectly confounded, and the drift inflates the B-favorable direction of the metric of record. The comment at `agent_footprint.py:171-176` states the format model: *"the same `message.id` appears on several lines with identical usage, and the tool_use blocks land on the final, most-complete copy."* **That is false.** Claude Code writes **one line per content block**, each line carrying the same `message.id`, the same `usage`, and a `content` list of **exactly one block**. There is no "most-complete copy". Last-wins therefore keeps only the *final* block of each assistant message and throws away every earlier one.

Measured over the 8 largest real transcripts in `~/.claude/projects/-Users-hosanglee-archy/`:

- 1828 of 1829 duplicate-id groups lose blocks under last-wins.
- **11.9% of all tool calls (367 of 3081) are invisible to the parser.**
- **4.7% of `Read`/`Grep`/`Glob` calls** — the numerator of the metric of record — are dropped.
- Loss is **not** a constant offset: it ranges 0% to 19% per session, tracking how much the agent batches parallel tool calls. That makes it a *differential* measurement error between arms, not a wash.

Exact reproduction (real `parse_transcript` vs. an identical parser that concatenates blocks instead of replacing them):

```
session   shipped                                     correct
e8897a68  pre_edit_reads=1 files=26 revis=72          pre_edit_reads=2 files=27 revis=76
2596212e  pre_edit_reads=1 files=20 revis=30          pre_edit_reads=1 files=22 revis=33
eeb03caa  pre_edit_reads=1 files=34 revis=131         pre_edit_reads=1 files=34 revis=133
0395265b  pre_edit_reads=1 files=11 revis=74          pre_edit_reads=1 files=11 revis=75
```

On `e8897a68` the metric of record is off by 100%. Fix: `deduped.setdefault(mid, []).extend(blocks)` with usage taken once per id (usage is genuinely identical across the lines — I checked; the token sums are the one thing the dedupe gets right).

This invalidates `pre_edit_reads`, `pre_edit_distinct_files`, `distinct_files_touched` and `file_revisitations` in **both** the #282 table and the #289 table.

## 2. CRITICAL — `input_tokens` is not a token measure. The §14.6 "net accounting is automatic" guard measures nothing.

Under Claude Code's prompt caching, `usage.input_tokens` on every assistant message after the first is a literal constant **2**. Prompt text — including an injected brief — lands in `cache_creation_input_tokens`, which the harness excludes by design.

Reproduction, first four assistant messages of five real sessions (`input_tokens, cache_creation, cache_read, output`):

```
msg_01GZFQAS11 (11262,  5170, 18348, 216)
msg_01MPoEEgRe (    2, 11968, 23518, 394)
msg_015vexPr99 (    2,   843, 35486, 371)
msg_012piF1Aed (    2,   394, 36329, 197)
```

The committed records confirm it: `input_tokens` is **0.0025%** of total input (A0: 88 vs 2,981,548 cache-read + 59,982 cache-creation), and `pre_edit_input_tokens` has a median of **37** across 30-66 turns.

Consequences:

- **`pre_edit_input_tokens` is a turn counter (~2/turn), not a token count.** Spec `docs/SPEC_AGENT_FOOTPRINT_BENCH.md:296-298` claims *"Because the brief is in the prompt, its tokens are already inside this sum: net accounting is automatic, which is the §14.6 guard made structural rather than bolted on."* A 581-token brief contributes **0** to this sum. §14.6 guardrail 7 ("Net, not gross… never report a reduction that excludes the brief") is the *only* anti-relabeling guard on arm C, and it is void. `agent_footprint.py:475-480` repeats the false claim in the `run_variant` docstring.
- **`footprint_tokens` ≡ `output_tokens`.** `corr(footprint_tokens deltas, output_tokens deltas) = 0.999984`; the sign vectors are identical. The "token footprint" headline is the output-token headline.
- The one field that *does* measure repo ingestion — `cache_creation_input_tokens`, i.e. new content entering the context window — is excluded from every metric. `bench/agent_footprint_results.md:171-176` asserts cache reads are *"dominated by prompt-cache behavior, not by how much of the repo the agent actually pulled in."* That reasoning may hold for `cache_read`; it does not hold for `cache_creation`, and the doc does not distinguish them. B0 created 77,824 cache tokens against A0's 59,982 — that difference is the agent pulling in more repo, and nothing reports it.

## 3. HIGH — the regression test encodes the same wrong format model as the bug it guards.

`tests/test_agent_footprint.py:217-239`, `test_streaming_duplicate_messages_counted_once`. The fixture at line 229 gives the earlier partials **empty** `content` and puts the `Read` on the final copy — precisely the format that does not exist. The test passes; the parser is wrong.

More broadly, the `_assistant` helper (`tests/test_agent_footprint.py:30-47`) emits one line with N blocks, e.g. line 85 `[("Read", "a.py"), ("Grep", None)]`. Real Claude Code never writes that. **Every parser assertion in the suite is against a synthetic format the tool does not produce**, which is exactly why three rounds missed defect 1. A fixture cut from a real transcript is the fix; the spec's own §11 asks for a "recorded/synthetic" fixture and only the synthetic half was built.

## 4. HIGH — the metric of record was swapped after the data was seen.

`agent_footprint.py:861` unconditionally appends `"Metric of record: \`pre_edit_reads\` (spec section 14.3)"` to **every** table, including A/B tables. But §14.3 designates `pre_edit_reads` as the primary metric for **arm C**. For the A/B refactor study, `docs/SPEC_AGENT_FOOTPRINT_BENCH.md:77` designates a different primary: `file_revisitations` — *"**primary metric.**"*

Chronology, from git:

- `records_282_flask.jsonl` landed in `144f61b` (2026-07-24).
- The string `"Metric of record"` entered `bench/agent_footprint.py` in `29f0973` — **after**.

And it matters directionally. `bench/agent_footprint_results.md:184` reads the study through `pre_edit_reads`: *"The metric of record leans B's way in direction (median −3.5 reads, 7 of 10 pairs)."* The study's actual pre-registered primary metric, `file_revisitations`, is **dead flat: 5/5, median −1.0, p=1.000**. The prose is more B-favorable than the pre-registered metric supports. The spec now carries two conflicting "primary metric" designations and the reporting code hardcodes the one that postdates the data.

## 5. MEDIUM — the task prompt's edit surface is exactly variant B's new file. Third unlisted confound, B-favorable.

`bench/agent_footprint/task_flask_endpoint_origins.md` asks for (a) endpoint→blueprint origin mapping and (b) a duplicate-endpoint check on URL-rule registration. Applying the patch and inspecting: `UrlRegistryMixin` in the new `src/flask/sansio/app_routing.py` contains `register_blueprint`, `iter_blueprints`, `add_url_rule`, `inject_url_defaults`, `handle_url_build_error` — the task's complete surface, in 190 lines, in a file whose docstring says *"so a routing or blueprint-registration change is one file."* In A the same surface is inside a 1013-line `app.py`.

The task and the patch landed in the same commit (`144f61b`), and `bench/agent_footprint_results.md:83-84` says the wording was *"fixed at run time"* — i.e. authored with B in hand. The prompt names no files (rule satisfied literally), but it was written against a known variant-B file boundary. `bench/agent_footprint_results.md:204` lists *"Two further confounds… both pushing toward the B-favorable direction"*; this is a third and it is unlisted.

**Honest weighting:** this confound favors B, and B still lost the token headline and tied on `file_revisitations`. It therefore *strengthens* the null rather than threatening it — but the doc's confound inventory is incomplete, and any future positive result on this task/variant pair would be uninterpretable.

## 6. MEDIUM — the committed artifact cannot be reconciled with its source, and `baseline_failed` is a default, not a measurement.

- No transcripts are committed. `bench/agent_footprint/` holds only the records, the patch, the task, and `run_tests.sh`. So `records_282_flask.jsonl` **cannot** be checked against the transcripts that produced it, and defect 1 above cannot be quantified for the actual published run.
- All 20 rows **lack** the `baseline_failed` key entirely (verified: `has baseline_failed field in file: False`). It defaults to `False` via `agent_footprint.py:135`. The field's own docstring says it exists so *"'0 regressions' is falsifiable from the artifact alone"* — but the only committed artifact predates it, so the published `"runs with the gate disabled by a red baseline: 0"` (`bench/agent_footprint_results.md:165`) is a default value, not a measurement. The fix is structurally right and retroactively inapplicable; the doc should say so.
- Internal consistency of the 20 rows is otherwise **clean**: no row violates `pre_edit_distinct_files ≤ distinct_files_touched`, `pre_edit_input_tokens ≤ input_tokens`, or `pre_edit_reads ≥ pre_edit_distinct_files`. Costs and durations are plausible and monotone in tokens. B4 (`input=411`, `pre_edit_input=359`) is an outlier but not impossible.

## 7. MEDIUM — the Bonferroni divisor of 9 counts three copies of one test.

`footprint_tokens`, `output_tokens` and `input_tokens` produce **identical** sign-test results on the #282 data: 4/6/0 and p=0.754 for all three (`bench/agent_footprint_results.md:155-157`), with `corr = 0.999984` between footprint and output deltas. Treating 9 metrics as independent is not defensible; the effective number is ~6.

Direction of the error: over-correction makes the one nominally significant cell (`pre_edit_distinct_files`, p=0.0078) look *less* significant (0.070 at ÷9 vs ~0.047 at ÷6). So it protects the reported null rather than manufacturing it — but `bench/agent_footprint_results.md:192-194` leans on "Bonferroni puts it at 0.070" as the reason to discount that cell, and that specific number does not hold up. The §12.7 breadth-confound argument in the same paragraph is the sound reason to discount it; the arithmetic one should be dropped or corrected.

## 8. LOW — spec/implementation divergences in the parser

- `agent_footprint.py:233` counts `pre_edit_distinct_files` from `Read` only. Spec §14.3 (`SPEC_AGENT_FOOTPRINT_BENCH.md:293`) says *"distinct file paths appearing in `Read`/`Grep`"*. Grep's `path` input is never read.
- `agent_footprint.py:240-241` increments `file_revisitations` for **any** file tool on an already-written path, including a second `Write`. Spec §5 (`:94-96`) says *"each time a `Read`/`Edit` targets a path already in `edited`"*. The implementation is arguably better; the spec should be amended to match rather than left divergent.
- `NotebookEdit` is in `_WRITE_TOOLS` (`:44`) but its input key is `notebook_path`, not `file_path`. It flips `made_edit` while contributing no file touch. Not reachable under `DEFAULT_ALLOWED_TOOLS`, so latent.
- No `isSidechain` filter. If `Task` is ever added to the tool surface, subagent tokens and tool calls fold into the parent run's metrics with no marker. No sidechain entries exist in the sessions I checked, so this is latent, not active.

## 9. LOW — sign test vs. Wilcoxon (asked, and it is defensible)

The sign test is the right call for the count metrics (`pre_edit_reads`, `distinct_files_touched`, `file_revisitations`) where ties are frequent and magnitudes are small integers. For `footprint_tokens` it throws away real magnitude information the doc itself laments (*"the token spread is the story"*, `:187`), and Wilcoxon signed-rank would be the standard, more powerful choice. But the sign test is **conservative** here, and the study reports a null, so this cannot have manufactured the result. Worth noting as a limitation; not a defect. §9 mandates the sign test, so changing it is a spec decision.

## Bottom line

Rounds 1-3 hardened the reporting layer thoroughly, and it is now genuinely solid. The prior held: the defects migrated **down** to the measurement layer, which nobody had attacked. `pre_edit_reads` is undercounted by a data-dependent margin, and `pre_edit_input_tokens` — the structural guarantee that arm C's brief can't be relabeled away — measures roughly two tokens per turn.

Neither defect flips the two published conclusions, both of which are nulls, and both undercounts are of a *sub*-metric rather than a reversal. But `docs/SPEC_AGENT_FOOTPRINT_BENCH.md:296-298` and `:332-335` currently promise a guarantee the telemetry cannot deliver, and any *future* positive arm-C result read off `pre_edit_input_tokens` would be an artifact.
